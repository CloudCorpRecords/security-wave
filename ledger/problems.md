## actionpin

### P-001 REAL (actionpin) Piped --json output truncates at exactly 65,536 characters, exit code stays 0
- Evidence: `npx -y @reneturcios/actionpin@0.1.0 audit <vscode-clone> --json` captured through a pipe returns exactly 65,536 characters on 3 of 3 trials, JSON parse fails with "Unterminated string", and the process exit code is 0. Same for cli/cli. Redirecting stdout to a file returns the full report (cli/cli: 121,537 bytes, parses, verdict PINNED, 229 actions). Every corpus repo whose report exceeds 64 KiB is affected: cli/cli, microsoft/vscode, vercel/next.js, facebook/react, PostHog/posthog (695,829 bytes), langfuse.
- Why it matters: pipes are the default consumption path for agents, scripts, and CI. Those consumers get corrupt JSON and a success exit code.
- Note: hookcheck (71,869 chars on langfuse) and injectcheck (62,184 chars on a large directory) delivered full output through pipes in the same harness, so this looks actionpin specific, not a shared factory flaw.
- Repro: `npx -y @reneturcios/actionpin@0.1.0 audit <any repo with 150+ actions> --json | wc -c` prints 65537 (with newline) instead of the true size.
- Status: FIXED in v0.1.2. The CLI printed with console.log and called process.exit() immediately, which discards whatever a piped stdout stream has not yet drained. Every report now goes through a flush-aware emit path and the exit code is applied with process.exitCode; a reader that closes the pipe early makes the process exit 141 instead of reporting success. Regression tests in test/pipe.test.ts spawn the real CLI with piped stdio and parse reports over 200 KiB. Re-validated on the published v0.1.2 at PostHog scale: piped and file captures both 632,283 bytes, identical bodies apart from the timestamp, 1,372 actions matching the Round 1 counts, and `| wc -c` now prints 632283. Evidence: ~/workspace/security-wave/actionpin-v012-fix-report.md

### P-017 REAL (hookcheck) Piped --json output truncates at exactly 65,536 characters on large reports

## New problems from Round 2

### P-018 REAL (hookcheck) ENV-EXFIL fires on co-occurrence of a token and a URL, driving COMPROMISED-PATTERN on own-automation estates
- Evidence: 15 findings drive all 5 COMPROMISED-PATTERN verdicts in the Round 2 corpus (langfuse 7, PostHog/posthog-js 3, attune-ai 2, cas 1, flowspec 2); 14 of the 15 are ENV-EXFIL. Every one was read against source. All are the target repo's own automation: git pushes with x-access-token to the repo itself or its own org's SDK repos, a workflow-dispatch POST to api.github.com/repos/<own repo> with the repo's own GITHUB_TOKEN in the Authorization header and a package name/version body, Slack status posts carrying release metadata and authenticated with the project's own bot token, a homebrew tap update pushed to the project's own tap, a seeder using documented public demo keys. In flowspec, the drivers are one-hop classifications of a 10,565-line CLI file that reads its own GITHUB_TOKEN (line 78), copies os.environ once (line 4241), and contains URLs in embedded doc templates.
- Mechanism: ENV-EXFIL requires only that a credential-shaped name and any URL or fetch co-occur in one finding. The P-002 fix made findings whole block scalars (often 30 to 100 lines), and one-hop following classifies whole referenced files, so co-occurrence is now the default state of any authenticated release step, with no requirement that the credential value flows into the send or that the destination is third-party.
- Why it matters: COMPROMISED-PATTERN again fires on major legitimate projects (langfuse, PostHog) with zero exfil-shaped evidence among the drivers, the same trust failure as P-003 and P-004 through a new rule. Genuinely exfil-shaped drivers in the corpus: 0 of 15.
- Repro: `npx -y @reneturcios/hookcheck@0.1.3 scan <langfuse clone> --json` verdicts COMPROMISED-PATTERN; the drivers are listed with source readings in round-2-hookcheck.md.
- Status: FIXED in v0.1.4 (flow semantics completed in v0.1.5, see P-047). ENV-EXFIL now requires the credential value to flow into a send: auth positions (Authorization headers, URL userinfo, auth flags) are scrubbed before atom collection, taint propagates through variable assignments, and destinations inside send call spans, curl or wget statements, stdin-reading pipelines, and print output next to a real send construct are the only paths that fire. The verdict narrowed with it: env references plus network behavior no longer reach COMPROMISED-PATTERN; the verdict needs a severe rule, a verified exfil flow, or credential store access combined with network behavior. A mirror rule CRED-EXFIL covers credential store contents piped or posted straight into a network send. 28 regression tests in test/round2.test.ts (32 after the P-047 addendum). Re-validated on the published binaries: all five Round 2 COMPROMISED targets verdict REVIEW on 0.1.5 (langfuse 336 findings, PostHog/posthog-js 187, attune-ai 160, cas 33, flowspec 99), with zero ENV-EXFIL or CRED-EXFIL findings across the ten-target re-validation set; A1 still verdicts COMPROMISED-PATTERN with the flow-verified ENV-EXFIL on the dropper. Evidence: hookcheck-v014-fix-report.md.

### P-019 REAL (hookcheck) Severe rules match patterns quoted inside defensive tooling, driving a COMPROMISED-PATTERN verdict
- Evidence: Smart-AI-Memory/attune-ai src/attune/hooks/scripts/security_guard.py (449 lines) is a defensive PreToolUse hook whose content is a pattern list for blocking dangerous shell commands (regexes matching eval(, curl and wget pipes, Invoke-Expression). It contains no network call of any kind (no urlopen, requests, socket, or http usage) and evaluates nothing. hookcheck 0.1.3 classifies it RISKY with REMOTE-EVAL ("evaluates content fetched from the network as code"), NET-FETCH, and OBFUSCATION, matching the quoted pattern text; that severe classification is one of only two drivers of attune's COMPROMISED-PATTERN verdict, and it is the only severe-rule finding in the entire 38-target corpus. The referencing workflow step is the project's own test harness piping test payloads, including the literal string "eval(x)", into the guard.
